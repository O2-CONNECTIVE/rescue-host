# 安全要件と接続停止の理由

[READMEへ戻る](../README.md)

**v0.2.1-devは新規接続を停止しており、本番利用できません。**
既存UptermではTCP転送先を`127.0.0.1:22`だけに強制できず、同一ユーザー権限の監視プロセスでは確実な失効も保証できません。
GUIと起動ワーカーの両方で開始を拒否し、設定や環境変数から解除するスイッチはありません。

## 保証できない境界

- Uptermの公開鍵認証は、OS上の最小権限化ではありません。
  旧SSH転送モードはPowerShellも起動するため、内側sshd認証だけを頼りにできません。
- OpenSSHの`authorized_keys`の`permitopen`などをUptermに渡しても、その制約は強制されません。
- オフラインモデルはSSHサーバー、実認証、Windowsサービス、OS権限分離、独立したタイマーを提供しません。
  呼び出し側の定期確認停止やPythonのハング、終了処理の無応答まで失効を保証しません。
- GUI終了や鍵ファイルの削除は、既存接続の終了証明ではありません。
  通信を終了しても、実行済み変更、切り離されたプロセス、取得された認証情報は取り消せません。

旧セッションは更新後も安全になりません。
[回復時のリスクと記録の扱い](recovery.md)を確認してください。

## 接続を再開する前の条件

実SSHのチャネル制約、固定宛先の強制、ゲストから保護されたWindows監督、内側sshdとヘルパーの権限制御、実接続と故障注入の検証が必要です。
モック試験の合格や利用者の承認だけで開始ゲートを解除しません。
詳細な受け入れ条件は既存の[バックエンド契約](SECURITY_BACKEND_CONTRACT.md)に集約しています。
